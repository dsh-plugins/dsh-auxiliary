### DSH-0.2.0-RC1-01 · Host packages cross to 0.2.0-rc.1; every `^0.1.x`-floored DSH peer is refused, and `^0.2.0` does not admit `0.2.0-rc.1`

- **Type**: breaking
- **Applies to**: every plugin whose `peerDependencies` declares `@deepseek-ai/dsh` or `@deepseek-ai/dsh-*` (the enforcement mechanism itself shipped in 0.1.7-rc.1 — [DSH-0.1.7-RC1-01](v0.1.7-rc.1.md); what is new here is the version boundary)
- **Touchpoints**: none (packaging/dependencies special surface — pre-flight §0 `peerDependencies` inventory)
- **Action level**: required-if-hit
- **Symptoms**:
  - Upgrading the host from any 0.1.x to `0.2.0-rc.1` disables every installed plugin whose DSH peer floor is `^0.1.x`: stderr shows `dsh: disabling profile plugin row "<id>": Plugin … is incompatible with dsh 0.2.0-rc.1: peerDependencies {...}`. The profile files are unchanged; the row silently stops mounting.
  - **The naive fix is refused too.** `^0.2.0` expands (semver ≥ 7.8.3, `includePrerelease: true`) to `>=0.2.0 <0.3.0-0`, and `0.2.0-rc.1 < 0.2.0` — so the rc host itself does not satisfy it. Measured against `0.2.0-rc.1` with the shipped `semver`:

    | Result | Ranges |
    |---|---|
    | Refused | `^0.1.0`, `^0.2.0`, `^0.1.0 \|\| ^0.2.0` |
    | Admitted | `^0.2.0-rc.1`, `>=0.1.0 <0.3.0`, `>=0.1.0 <0.3.0-0`, `*`, `workspace:*` / `workspace:^` (treated as the running version) |

    `^0.2.0-rc.1` also admits the future `0.2.0` final and 0.2.x patches, so it is the recommended floor form for the whole 0.2 window.
- **Migration recipe**:
  1. Rewrite each DSH peer as `^0.1.0 || ^0.2.0-rc.1` (keeps 0.1.x hosts installable) or `^0.2.0-rc.1` (0.2-only).
  2. Ship the peer fix as a plugin release; the host re-reads the installed `package.json` on the next boot — no exemption needed.
  3. If you must run a mismatching build now, `dsh plugin allow-version <name>@<version> --dsh-version 0.2.0-rc.1 --accept-risk` (profile-scoped, exact-version; see [DSH-0.1.7-RC1-01](v0.1.7-rc.1.md#dsh-017-rc1-01--dsh-peer-ranges-are-enforced-at-install-and-at-startup-017-does-not-admit-017-rc1) for the full grant mechanics).
- **Verification**: restart the host and assert stderr has no `disabling profile plugin row` line for your ids; `--dump-config` cannot detect a denial (see the rc.1 card's Verification section).
- **Source**: all `packages/*/package.json` version bumps at `dsh-v0.2.0-rc.1`; checker unchanged from rc.1 ([`packages/boot/app-boot/src/plugin-compatibility.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.1/packages/boot/app-boot/src/plugin-compatibility.ts)).
- **Field note** (first-hand, 2026-09-28): `@dsh-external/dsh-vision` (registers `view_image`) was disabled twice on the upgrade path — v0.1.0 with `^0.1.0`, then v0.1.1 with `^0.2.0` — and mounts again after shipping v0.1.1 with `^0.1.0 || ^0.2.0-rc.1`. The other six fleet plugins carry no DSH peers and were never refused.

### DSH-0.2.0-RC1-02 · Web work-details default moves to `detailed`; the saved `transcriptView` setting becomes optional

- **Type**: behavior
- **Applies to**: plugins that read the Chat settings schema (`transcriptView`) or assume the `standard` default; browser surfaces rendering transcripts
- **Touchpoints**: #5 (UI — Chat settings schema) if your plugin mirrors the field
- **Action level**: optional
- **Symptoms**: fresh Web clients (non-Desktop) now render `detailed` work details; the schema field becomes optional (`transcriptView?`) and the schema no longer carries a `.default(...)` — absence defers to the client default (`DEFAULT_TRANSCRIPT_VIEW_MODE = 'detailed'`, or `standard` when `dshDesktop` is present). The legacy saved value `normal` now maps to `detailed` instead of `standard` (`expanded` already mapped to `detailed`).
- **Migration recipe**: plugins that hard-code a `standard` fallback should not assume a schema default any more — treat an absent value as "client default" (`DEFAULT_TRANSCRIPT_VIEW_MODE` on Web, `standard` on Desktop); plugins that persist the field may now omit it.
- **Verification**: fresh profile + fresh browser: transcript renders `detailed` without a saved setting.
- **Source**: [47db27a73](https://github.com/deepseek-ai/deepseek-harness/commit/47db27a73) `fix(ui-chat): resolve work-details defaults in client code`, [b066690f7](https://github.com/deepseek-ai/deepseek-harness/commit/b066690f7) `fix(web): default fresh work details to detailed`, [a03e63d1e](https://github.com/deepseek-ai/deepseek-harness/commit/a03e63d1e) `fix(ui-chat): map legacy normal work details to detailed`.

### DSH-0.2.0-RC1-03 · Schedule/time-context/ui-schedule rows leave the default web-app bundle; they ship as an optional bundle

- **Type**: breaking
- **Applies to**: plugins and user patches that insert rows before/after the `schedule`, `time-context`, or `ui-schedule` ids, or that assumed those services exist in a default web profile
- **Touchpoints**: none (packaging/composition special surface — profile patch row ids)
- **Action level**: required-if-hit
- **Symptoms**: the three rows were already shipped `disabled: true` at `dsh-v0.1.7-rc.2`, so default profiles see no runtime change; they are now removed from `packages/bundle/web-app/cordis.patch.yml` entirely and ship in the optional bundle `@deepseek-ai/dsh-experimental-schedule-bundle`. The real break is for user patches or plugins that re-enabled these rows by id (`disabled: false` on `schedule`/`time-context`/`ui-schedule`) or inserted relative to them: there is no such row to override any more, and the Schedule service they turned on is gone.
- **Migration recipe**: install `@deepseek-ai/dsh-experimental-schedule-bundle` where the feature is wanted (and drop the by-id re-enable patch), or drop the dependency. Bundle authors: re-run your row-id inventory against the new patch files before inserting.
- **Verification**: `dsh --profile web --dump-config` contains no `schedule`/`time-context`/`ui-schedule` rows on a default profile.
- **Source**: [41c29fa83](https://github.com/deepseek-ai/deepseek-harness/commit/41c29fa83) `feat(schedule): ship the Schedule switch as an optional bundle` and the schedule-bundle commit series; [`packages/bundle/web-app/cordis.patch.yml`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.1/packages/bundle/web-app/cordis.patch.yml).

- **Type**: capability
- **Applies to**: bundles and plugins that insert into the same composition, plugin-manager duplicate-id diagnostics

- **Action level**: informational
- **Symptoms**: `dsh-base` gains an `otel` row; `dsh-web-app` gains `desktop-product-telemetry` and `product-analytics` rows, both `disabled: !!js` unless the profile is `desktop`. ### DSH-0.2.0-RC1-06 · Explorer path-opening spawns visible; the native-command runner gains a visibility argument — retire local reveal hotfixes

- **Applies to**: fleet installs carrying local patches to `@deepseek-ai/dsh-native-command` that passed raw paths or forced `windowsHide: false` so reveal/open shows a window

- **Action level**: optional

### Desktop note A — Desktop host: the plugin-visible `ctx.sessions` registry is empty — plugins resolving the session cwd through `sessions` fail on Desktop while working on Web

- *Type*: breaking
- *Applies to*: every plugin whose host half resolves the running session (or its workspace cwd) via `ctx.sessions.get(sessionId)`; install flows that rely on such plugins on the Desktop profile
- *Touchpoints*: #3 (services — service resolution), special surface: the Desktop runner (`dsh-desktop-host` → `runProfile`) instead of the CLI app-boot
- *Action level*: required-if-hit
- *Symptoms*:
  - On the Desktop host, `ctx.sessions.get(id)` returns `undefined` for **every** id, including a session the same host is actively running (its `session.v4.jsonl.zstd` is being appended at that moment). The plugin's cordis `inject: ['webServer', 'loader', 'sessions']` still resolves and the plugin activates — a service named `sessions` exists, but its live-session registry reads empty from a plugin fiber.
  - The Web host with the identical dsh version, profile bundles, and plugin tree works: the same probe flow (batch → file PUT → commit) completes and files land under `<workspace>/.dsh/tmp/attachments/`.
  - User-visible: a paste/attachment plugin's chips render but resolve "unavailable" (no file is ever written) and sending fails.
  - Unverified suspicion: the Desktop runner boots the composition with a different cordis fiber/isolate layout than the CLI app-boot, so the `sessions` service a plugin resolves is not the registry the agent runtime populates.
- *Migration recipe*: plugin-side workaround, verified first-hand — no host changes needed.
  1. **Session resolution fallback**: when `ctx.sessions.get(sessionId)` misses, resolve the workspace through `ctx.get('workspaceRegistry')` — the registry maps header-validated `sessionIds` to canonical workspace `path`s (`resolve(workspace.path)` is the cwd). Still entirely server-side: no client-supplied path enters the resolution, so the original security model holds. Keep the canonical lookup first; the fallback changes nothing on Web.
  2. **Binary request bodies do not survive `dsh-app://` forwarding either**: a Blob PUT arrives with a declared `Content-Length` that no longer matches the received bytes (the body is re-encoded in a text-safe way), so any size/content validation rejects it. Ship a base64-JSON transport for the Desktop origin (`location.protocol === 'dsh-app:'` detection; e.g. `POST .../files/<n>/base64` with `{ "data": "<base64>" }`, server decodes and checks the decoded length against the declared size) and keep the binary fast path on Web. Verified end-to-end: paste → upload → commit → file lands under `<workspace>/.dsh/tmp/attachments/`.
  3. Track the upstream reports: [discussion #8303](https://github.com/deepseek-ai/deepseek-harness/discussions/8303) (includes the confirmed workaround) and the companion issue in the dsh-external beta channel.
  4. Re-verify after every Desktop release: one `POST` against the plugin's session-resolving endpoint with a live session id is enough to see `200` vs the `live session not found` family of failures; once the host registry is fixed the fallback simply stops firing.
- *Verification*: on the Desktop host, with one session running, call a plugin endpoint that starts from `ctx.sessions.get(sessionId)`; assert the resolved session and `session.header.cwd`. `--dump-config` cannot see this: the plugin mounts and serves; only the session lookup fails.
- *Source*: observed first-hand on DeepSeek Harness Desktop 0.2.0-rc.2 (Windows) against the bundled runtime; [`packages/api/session-controller`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.1/packages/api/session-controller) and the Desktop runner entry at `dsh-desktop-host` at `dsh-v0.2.0-rc.1`.
- **Field note** (first-hand, 2026-09-29): unauthenticated probes against the Desktop host (127.0.0.1:19387): `GET /dsh-paste-input/v1/latest → 200` (host half mounted), `POST /dsh-paste-input/v1/batches → 400 "live session not found: <id>"` for both a live and a persisted session id. Same probes on the Web host (port 3080, same rc.2) complete the whole upload flow. Reported upstream as [discussion #8303](https://github.com/deepseek-ai/deepseek-harness/discussions/8303).

### Desktop note B — Desktop host spawns tool subprocesses with a minimal `PATH`; `pwsh` is not resolvable on Windows

- *Type*: behavior
- *Applies to*: plugins and skills whose host-side code shells out to platform tools resolved from `PATH` (package managers, shells, git); anything assuming the CLI login-shell environment on Desktop
- *Touchpoints*: #7 (subprocess)
- *Action level*: conditional
- *Symptoms*: subprocesses spawned by sessions on the Desktop host see a minimal `PATH` — `System32` tools resolve, but `pwsh` does not (`spawnSync pwsh ENOENT`). The 0.2.0-rc.2 release notes fix the missing login-shell environment for macOS/Linux graphical launches; Windows Desktop appears to still need the equivalent.
- *Migration recipe*: resolve executables by absolute path when the environment is known (derive from well-known install locations), or degrade with a clear message instead of relying on `PATH` lookup on the Desktop profile.
- *Verification*: from a Desktop-hosted session, spawn `pwsh -Command `$PSVersionTable.PSVersion`` and observe ENOENT; the same spawn from a Web-hosted session succeeds.
- *Source*: observed first-hand on Desktop 0.2.0-rc.2 (Windows); [`apps/desktop/README.md`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.1/apps/desktop/README.md) and the macOS/Linux login-shell fix in the [rc.1 → rc.2 compare](https://github.com/deepseek-ai/deepseek-harness/compare/dsh-v0.2.0-rc.1...dsh-v0.2.0-rc.2) (`fix(desktop): supply login shell environment on macOS and Linux graphical launches`).
- **Field note** (first-hand, 2026-09-29): a tool subprocess under the Desktop host failed `spawnSync pwsh` with ENOENT while `netstat`/`wmic` (System32) resolved normally; the identical spawn from the Web host worked.
